## 【重要纠错】离线双击打不开 dist/index.html —— 我此前的承诺是错的

### 事故与责任
我在交付总结中声称「`base: './'` 保证离线双击可开」。**这是错误的**。用户实际双击报错，我需为此负责。
根因：`base: './'` **只解决路径解析**，解决不了 **ES 模块在 `file://` 下的跨源拦截**。
`<script type="module">` 在 `file://` 协议下 origin 为 `null`，按跨源请求处理，无 CORS 头即被拒绝 → 白屏。

### 修复方案（已落地并验证）
1. 安装 `vite-plugin-singlefile`（devDep）
2. 新增 `vite.config.offline.ts`：将 JS/CSS 全部内联进单个 HTML，产出 `dist-offline/index.html`
3. 新增 `npm run build:offline` 脚本
4. `.gitignore` 补 `dist-offline`

### 二次踩坑：动态 `import()` 会让单文件内联失效
首次内联后仍白屏，实测捕获真实异常：**`SyntaxError: Cannot use 'import.meta' outside a module`**。
根因：`src/ui/pages/AiAssistantPage.tsx:220` 有 `await import('@/ui/clipboard')`，
Vite 为动态导入注入 `import.meta.url` 预加载 helper；而 `import.meta` 在**非模块脚本**中直接抛语法错误。
→ 已改为静态导入 `import { writeClipboard } from '@/ui/clipboard'`；
   `vite-plugin-singlefile` 只有在**零动态 import** 时才能产出纯内联脚本。
**结论：源码中禁止使用动态 `import()`**（本项目单文件离线目标下）。

### 验证方法（可复用的关键手法）
jsdom **没有 `indexedDB`**（且 `file://` 下 `localStorage` 抛 SecurityError），

### 最终门禁

## 【第四轮】用户报告「AI 助手返回都为空」→ 挖出 4 个缺陷（含 1 个我自己的误判）

### 用户症状

### 诊断过程与决定性证据（本机真实 Ollama 0.32.7）
模型清单：`qwen3.5:9b`（**capabilities 含 vision/completion/tools/thinking**）、`qwen3.5:9b-max`、`qwen2.5:14b-full`、`qwen2.5:14b-max`、`qwen2.5-coder:7b-instruct-q4_K_M`。

**D1（真凶）max_tokens=1024 截断推理模型 —— 但只调 max_tokens 治不好**
| 条件 | finish_reason | completion_tokens | content |
|---|---|---|---|
| 简单问题 max_tokens=1024 | length | 1024（打满） | **空** |
| 简单问题 max_tokens=4096 | stop | 1629 | 正常 59 字符 |
| **真实 prompt**（2,102 prompt tokens）max_tokens=4096 | length | 1994 | **空**（reasoning 7790 字符） |
| 同上 max_tokens=8192（num_ctx 仍 4096） | length | 1994 | **空**，`total_tokens` 仍卡 4096 |
| 同上 + `OLLAMA_CONTEXT_LENGTH=16384` | length | 4096（打满） | **空**（reasoning **16514** 字符） |

→ 两个隐性约束：
1. **Ollama `num_ctx` 默认 4096**（启动日志 `vram-based default context default_num_ctx=4096`），是它而非 `num_predict` 在卡；`total_tokens` 恰等于 4096。
2. **OpenAI 兼容端点不接受 `options.num_ctx` 覆盖**（实测被忽略）→ 只能服务端 `OLLAMA_CONTEXT_LENGTH`。
3. **`qwen3.5:9b` 在该任务上思考不收敛** —— 给多少配额吃多少，加 max_tokens 是无底洞。

**真正的修法（三组对照实验）**
| 请求 | finish_reason | content | 耗时 |
|---|---|---|---|
| 兼容端点 + `reasoning_effort:"none"` | stop | **1322 字符** ✅ | **10.9s** |
| 原生 `/api/chat` + `think:false` | stop | 1276 字符 ✅ | 10.7s |
| 兼容端点 + `think:false` | length | **0 字符** ❌ | 28.1s |

→ app 只用兼容端点，故 **`reasoning_effort: "none"` 是唯一可用路径**。`think:false` 在兼容端点上无效。

**兼容性验证（重要，决定能否默认开启）**
- 非推理模型（`qwen2.5-coder:7b`、`qwen2.5:14b-full`）带 `reasoning_effort:"none"` → **200 + 正常正文**，不会被打挂
- 推理模型关掉思考后 `message` 的 keys 只有 `['role','content']`，**不再返回 reasoning 字段**
- 风险：`reasoning_effort` 并非所有 provider 都认 → 必须有「4xx 时去掉该字段重试一次」的降级

**D2 双击版（file://）无法直连本机 Ollama —— CORS，前端无解**
- Ollama 白名单含 `file://*`，但浏览器从 file:// 页面发出的是 **`Origin: null`** → 不匹配 → **403 且不带 CORS 头** → 前端只见 `TypeError: Failed to fetch`
- curl `-H "Origin: null"` → 403；真实 Chrome file:// 页面 → FETCH_FAIL；http:// 页面 → 200
- **解法：`OLLAMA_ORIGINS=*`** 重启后 → `Access-Control-Allow-Origin: *`，file:// 页面 **200 OK**
- 前端唯一能做的是**给出可操作提示**，不要试图绕过浏览器限制

**D3 无 Key 本地服务被误判离线（两处闸门，缺一不可）**
- `aiClient.ts:314` 无 Key → 直接 `NO_KEY` 离线，与同文件注释「兼容 Ollama 无 Key」自相矛盾
- **`useAiAvailability.ts:99-111` 在调用 probeAi 之前就短路了同样逻辑** → 只改 aiClient 完全无效

**D4 probeAi 兜底用 `maxTokens:1`** → 对推理模型必然 content 空 → 误判服务不可达。探测的目的是连通性而非内容。
**D5（工程师顺带发现）** 兜底不校验模型名 → 错选模型会致兜底失守。

### 用户已拍板
1. `max_tokens` 默认 **4096** + 设置页可调
2. 无 API Key 的本地服务**允许**进 AI 模式（baseUrl 非空即视为已配置）

### 新增环境坑
- **Windows 版 Python 读不了 Unix 风格 `/tmp` 路径** → 落盘文件必须用 Windows 路径（如 `E:/...`）；Windows `curl -o` 也不认 `/e/...`，需先 `cd` 再用相对文件名
- **MSYS 参数转义**：`tasklist //FI` 会被转成路径报「无效参数」→ 用 `export MSYS2_ARG_CONV_EXCL='*'` 后写 `tasklist /FI`
- 杀 Ollama 后端口释放有延迟，立即重启会 `bind: Only one usage of each socket address`

### 端到端验证方法论（零依赖 CDP，可复用）
Node 22 自带全局 `WebSocket`，可以**零依赖**驱动 Chrome DevTools Protocol：
1. `spawn(chrome, ['--headless=new','--disable-gpu','--no-proxy-server',`--remote-debugging-port=9223`,`--user-data-dir=<dir>`,'about:blank'])`
2. 轮询 `http://127.0.0.1:9223/json/list` 拿 `webSocketDebuggerUrl` → WS 连接
3. `Runtime.evaluate` + `Page.navigate`；MUI 受控输入要用 **native setter trick**：
   `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set.call(el, v)` + `dispatchEvent(new Event('input',{bubbles:true}))`
4. 关键教训：**首屏配置为空时应用正确地落在离线闸门**（`data-testid="ai-assistant-offline"`），
   所以不能直接等 `ai-assistant-page` —— 要先等 `#root` 有内容，写入 localStorage 配置后 reload，再等 AI 模式。
5. 配套写一个**本地模拟 OpenAI 服务端**捕获应用真实发出的请求体 → 这是验证「接线类缺陷」的最强手段：
   不依赖真实模型、不占用 Ollama、可断言请求体字段。
