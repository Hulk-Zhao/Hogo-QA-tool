### 6.4 方法教训（重要）

「PDF 里 `/Subtype /Image` 计数」是**坏代理**：空画布（只有坐标轴）也会被 Chrome 光栅化成位图对象。

**正确做法：把 PDF 渲染成 PNG，再用 vision skill 逐页看图。** 本项目铁律应补一条：

> 涉及图形的产物，必须**渲染出来看**，不能用字节模式计数代替视觉核验。

`diag-charts.mjs`（屏幕 / print 媒体 / PDF 三态对比）、`diag-pareto.mjs`（逐图裁剪截图 + 与独立页对照）、
`diag-stale.mjs`（离线包 `file://` 场景复现）、`diag-resize.mjs`（resize 期间画布是否变空）、
`pdf-inspect*.py`（PDF 逐页位图尺寸 / 文字 / 渲染成 PNG）。

`p0-verify.mjs` 增加**自包含**判据 `chartColorInk`：统计画布中强饱和像素数（数据系列是蓝柱/红线；

> 附带发现：该判据若在图表刚挂载时立即测量，会读到动画首帧（实测 `[581, 402, 0]`）。
> `animation: false` 之后已稳定，脚本中另加 1.2s 兜底等待。

### 10.2 P2-A 规格限自动预填（本轮最重要的用户缺陷）

### 11.2 P3-C 打印 / PDF：三条实测根因

1. **画布尺寸 = 最后一次观察到的容器宽度**。Chrome 打印时**不派发 window resize**

### 11.3 P3-A DeepSeek HTTP 400：按服务端区间自动收敛后重试

用户截图证据：`HTTP 400: Invalid max_tokens value, the valid range of max_tokens is [1, 393216]`。

根因：「最大输出 tokens」按需求**刻意不设上限**（`sanitizeMaxTokens` 只校验 `>= 1`），
而各家上限差别极大（本机 Ollama 基本不限、DeepSeek 393216）→ 用户填大值必然被拒，
且界面只回一句「请检查模型名与参数」，用户无从下手。

### 12.2 打印无图 = 上一轮（P3）修法引入的回归：异步重挂载 → 同步光栅快照

**P3 探针为什么会「全绿」**（教训，务必保留）：`p3-print-verify.mjs` 在 `Page.printToPDF` 之前先
`Emulation.setEmulatedMedia({media:'print'})` + `sleep(1500)`，等于**提前**把页面切进打印态并给了重绘时间。
真实 Ctrl+P 没有这一段 —— 那些 `ok=true` 是**假阳性**。

**改用真实路径复现**（`.probe/p4-print-truth.mjs`：不预置媒体、不 sleep）拿到的事件时间线：

```text
3069ms beforeprint     .print-chart canvas = 3 块（还是屏幕那张 449×300）
3097ms mq-change(true) .print-chart canvas = 0 块  ← 旧图被卸载、新图还没画
3204ms afterprint      .print-chart canvas = 0 块
```

根因：P3 的 `key={printing ? 'print' : 'screen'}` 在 `beforeprint` 里**卸载旧图表再挂载新图表**，
而 React 提交 + zrender 重绘是异步的（组件上还挂 `lazyUpdate`，把 `setOption` 推迟到下一帧）
→ Chrome 取快照那一刻 DOM 里一块画布都没有 → 纸上只剩卡片标题。

**P4 的修法**（`src/ui/charts/printLayout.ts` 整体重写）：

1. 完全不碰 React（三个图表组件里的 `key={printing…}` / `usePrintLayout` 全部删除，屏幕态恒定）；
2. 在 `beforeprint` 回调里**同步**对每块已渲染画布调用
   `echarts.getInstanceByDom(el).getRenderedCanvas({ pixelRatio, backgroundColor })`；
3. 同一卡片的多块位图纵向拼成一张白底画布；把**画布元素本身**插进 `.print-chart`
   （不是 `<img>`：data URL 解码是异步的），并给宿主加 `.has-print-snapshot`；
4. 全程同步、无微任务、无 rAF；`afterprint` 原样移除。
5. 拿不到 ECharts 实例时**退化直接搬像素**，绝不产出空白。
6. `src/ui/layout/AppShell.tsx` 里 `useEffect(() => ensurePrintSnapshotBinding(), [])` 全局接线，
   覆盖任意页面的任意图表。

DPI 契约：位图按「逻辑宽 → 约 2200px」选 1~6 倍像素比（`PRINT_TARGET_RASTER_PX`），
打印时 `width:100%` 铺满 A4 可打印区（186mm ≈ 300 DPI）。

### 12.3 Excel 无图 = OOXML 内容类型违规（openpyxl 查不出来的那一类）

`[Content_Types].xml` 里**没有** `xl/drawings/drawing1.xml` 的 `Override`，于是它按
`<Default Extension="xml" ContentType="application/xml"/>` 被声明成 `application/xml`，
违反 OOXML 规范（应为 `...drawing+xml`）。**Excel / WPS 判定违规后会把整张 drawing 丢掉**
→ 用户一张图都看不到；而 **openpyxl 是按 workbook/sheet 关系去找 drawing 的、根本不读内容类型**
→ 我们此前的组件测试与 openpyxl 校验全绿，和用户观感完全相反。

- 实证（修复前）：`.workbuddy/tmp/ooxml_strict.py` 对 P3 产物报
  `violations=1 / GENERIC_CONTENT_TYPE / xl/drawings/drawing1.xml`（见 `.probe/p4-xlsx-ct-before.json`）。
- 修法：`src/data/exporter/excelImages.ts` 现在**同时**登记 sheet 与 drawing 的 `Override`，
  并加 `if (!patchedTypes.includes('</Types>')) throw` 守卫。
- 旁证：SheetJS 自己写出的 `[Content_Types].xml` 里 png 有 `Default`；
  MS-OI29500 明确「仅当内容类型为 `...drawing+xml` 时客户端才应加载 drawing」。
- **诚实口径**：本机没有 Excel / WPS / LibreOffice，**无法直接实测**打开效果，
  验收代理 = 上述严格校验器 + 「按 Excel 的解析规则 0 违规」。WPS 未实测这一点已写进 12.10。

**顺带纠正上一轮的测量错误**：`p3-pdf-ink.py` 直接读 PDF 里的**位图对象**（zrender 画布带 alpha，
`extract_image` 拿到无 alpha 的底图 → RGB≈(0,0,0)）→ 一律被判成「墨」→ inkRatio 0.999。
正确做法是**先渲染 PDF 页再量**（`.workbuddy/tmp/render.py` + `.workbuddy/tmp/ink.py`）。
标定值：已知好图 `p3-xlsx-image1.png` → `inkRatio 0.4371 / coloredRatio 0.0237`。

### 12.5 二次验收新发现：第一次打印多出一张全空白页（本轮第三个真实缺陷）

12.2 修好之后复跑打印探针，发现 **`ok=false`：第 2 页墨迹 0.0001（全空白）**，
图表被推到第 3 页。这不是偶发：连跑 3 次结果完全一致（5 页，`p2=0.0001`）。

**定位过程**（`.probe/p4-pagination.mjs` 量版面几何 + `.probe/p4-one.mjs` 做 A/B）：

- 报表页图表区原本带 `className="print-page-break"`（`break-before: page`）；
- 每个场景都跑**全新页面上的第一次打印**（这一点很关键，见下）：

| 场景 | 页数 | 说明 |
|---|---|---|
| as-is（Stack 带 `print-page-break`） | **5** | 第 2 页墨迹 0.0001（全空白） |
| 去掉 `break-before` | **4** | 无空白页 ★ 采用 |
| 改成 `display: block`（CSS `!important`） | 5 | 与 display 无关 |
| 改成 `display: flex`（内联） | 5 | 同上 |
| 给快照 canvas 限高 `max-height:190mm` | 5 | 与高度无关 |
| 把 `break-before` 挪到前面一个空 div | 5 | **挪位置也没用** |
| 图表卡片 `break-inside: auto` | 5 | 不是 `break-inside` 的锅 |

结论：**成因就是 `break-before: page` 本身**。另外发现一个陷阱：
如果把多个场景放在**同一个页面**里连续打印，第二次之后空白页会「自己消失」
（第一次打印时 Chrome 会把布局宽度切成 859→703 再重排，ECharts 尺寸随之变化），
**因此验证这类分页问题必须每次都用全新页面**，否则会得出「改了没用 / 没改也好了」的错误结论。

**修法**（最小改动，2 处）：

- `src/ui/pages/ReportPage.tsx`：图表 Stack 去掉 `className="print-page-break"`；
- `src/print.css`：保留 `.print-page-break` 的定义但在注释里写明「报表页不得使用」，
  并把整段 A/B 证据写进文件，避免以后有人「照着旧代码加回来」。

代价：图表区不再强制另起一页。实测本数据集下**图表仍然落在第 2 页**（第 1 页正文本来就满了），
所以观感不变，却少了那张空白纸。卡片级 `break-inside: avoid` 仍在，图不会被拆成两页。

### 13.3 P5-B：「AI 返回内容无法解析」的真凶

旧代码在 200 分支用 `await response.json()`。**只要服务端（或反向代理）返回
`text/event-stream`，`json()` 必然抛错**，于是统一被压成一句
「AI 返回内容无法解析。」——用户拿不到任何可自助排查的信息（DeepSeek 侧尤其常见）。

修法（`src/services/ai/aiClient.ts`）：
1. 先 `await response.text()` 读原文，再 `JSON.parse`；
2. 解析失败时**尝试按 SSE 解析**（逐行取 `data:`、跳过 `[DONE]`、累加
   `choices[0].delta.content`，兼容伪流式的 `message.content`），能拼出正文就当成功；
3. 仍失败才报错，并把**原文片段**（折叠空白、≤200 字符）同时写进
   `errorMessage` 与 `serverDetail`；
4. 新增「200 且 JSON 合法但没有 `choices`」的专门文案（不再与「内容为空」混淆）；
5. 只是 SSE 形态但没有正文 → 走「返回内容为空」，不误导用户去查网络。

副作用：`FetchLikeResponse.json` 不再是 200 分支的必经路径，测试里 4 处 mock 与
5 处断言需要按真实语义（`text()` 与 `json()` 返回同一份原文）补齐。

### 14.1 P6-A：Word 报表内嵌图表（用户「报表打印和 excel 导出都没有图片」的最后一环）

改法：`buildAiReportDocx(model, analyses, meta, options)` 新增第 4 参
`{ charts?: readonly ChartImage[] }`，把 `collectChartImages()` 采到的页面快照 PNG
写进 `word/media/imageN.png`，并在正文「附：未生成分析的模块与原因」之后插入
「图表」一级标题 + 每张图一个居中段落（含图题）。

**踩过的 4 个坑（都与「Word 直接判文件损坏 / 图丢失」有关）**：

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | `[Content_Types].xml` 漏 `<Default Extension="png" .../>` | 整张图被 Word 丢掉（不是报错，是静默丢） | 无条件声明 png 默认项（未使用时无害）；P4 在 Excel 的 drawing content-type 上踩过同款 |
| 2 | 图片关系 id 与 styles 抢 `rId1` | Word 判文件损坏 | 图片关系用独立前缀 `rIdImg{i}`，`rId1` 只留给 styles |
| 3 | `word/document.xml` 根元素不声明 `xmlns:r` | `r:embed` 前缀无定义 → 判损坏 | 根上补 `xmlns:r=.../officeDocument/2006/relationships`（wp/a/pic 三个前缀内联声明在 `wp:inline` 那一层即可） |
| 4 | 直接按像素 × 9525 EMU 落图 | 快照宽 2364px ≈ 22.5cm，超出 A4 可打印宽 | `fitImageSizeEmu()` 按「装进 16.5cm × 20cm」**等比**收敛（竖长控制图按高度钳制），非法输入兜底为正数 |

**测试与证伪**：`docxReport.spec.ts` 10 → 16 条（媒体字节逐字节一致、rels 不撞号、
content-type 有 png、`r:embed`、图表位置在分析之后免责声明之前、尺寸钳制与非法输入、
空图题兜底与转义）；`AiExportPanel.spec.tsx` 新增「第 5 参必须带 charts」；
变异 **M38–M45** 共 8 条全红。

**真机验收（`.probe/p6-word-charts.mjs` + `.probe/p6-docx-charts-verify.py`，11/11 PASS）**：

| 项 | 实测值 |
|---|---|
| 页面可采集图表数 vs Word 内嵌图片数 | 2 == 2（控制图卡片 2 画布拼 1 张 + 能力图 1 张） |
| .docx 字节 | **107,609**（P5 纯文字版 18,809 → 图片确实进去了） |
| word/media/image1.png / image2.png | 67,314 / 18,701 字节，均为真 PNG |
| python-docx `inline_shapes` | 2，尺寸 5940000×2591446 / 5940000×1626005 EMU（宽度都=16.5cm，未溢出） |
| vision 复核内嵌首图 | X-bar & R 控制图，数据点 + CL/UCL/LCL 清晰，中文无乱码、无空白 |

### 14.2 P6-B：打印分页与留白

**先修测量口径（这本身就是「4~5 页浮动」假象的根源）**：
`.probe/p4-print-truth.mjs` 把渲染目录里**上一轮残留**的 `p5.png` 也数成新页，
于是真 PDF 4 页被报成 5 页（该 PNG 时间戳是 09-19 16:35，而本次渲染是 09-20 15:43）。
已修：渲染前清空目录；新探针 `.probe/p6-print-pages.mjs` + `.workbuddy/tmp/p6-pagegeom.py`
按「文字 bbox ∪ 图片 bbox」的最低边量**每页真正用到哪一行**（页数只说明有几张纸，说明不了留白在哪）。

**基线（真机、`dist-server`、真实打印路径）**：4 页，利用率 99.2% / 92.4% / **68.7%** / 48.3%。
第 3 页尾部空 **242pt（8.5cm）**：两张「原始尺寸 / 原始不良」预览表在屏幕上是
「限高 320px + 滚动」的预览框，整块约 266pt，第 3 页只剩 242pt → 浏览器只能整块推页，
连标题都成了孤儿。

**两种改法的实测取舍**：

| 改法 | 结果 | 结论 |
|---|---|---|
| 打印态完全去掉限高（把屏幕预览的 120 行全印出来） | 4 页 → **8 页**，每页也都 95%+ 饱满 | 分页确实是「按内容高度」了，但与第三轮记忆「原始明细表限 200 行 —— **防止打印分页爆炸**」的既有设计意图冲突，弃用 |
| 打印态「可跨页 + 每张表最多印 24 行 + 纸上写明只印了前 24 行」 | **4 页**不变，利用率 99.2% / 92.4% / **96.0%** / 85.5% | **采用** |

采用项的实现（三处必须成对，缺一不可）：
1. `src/print.css`：`.print-table-split` 及其 `table/tbody/容器` 打印态 `break-inside: auto`，
   容器 `max-height: none` + `overflow: visible`，`thead` 改 `table-header-group`（表头每页重复），
   `th` 取消 sticky；`tbody tr:nth-child(n + 25)` 隐藏第 25 行起的内容；
2. `src/services/report/previewLimits.ts`（新）：`PRINT_PREVIEW_LIMIT = 24` 与 `RAW_PREVIEW_LIMIT = 200`
   放在 services 层，好让用例把 CSS 文本与常量对起来验证；
3. `src/ui/pages/ReportPage.tsx`：两张预览表在行数超上限时渲染**只在打印态显示**的
   `print-cap-note-raw-*` 提示（「共 N 行，打印仅含前 24 行；完整数据请用「导出 Excel」」）。

**新护栏（`.probe/p6-print-pages.mjs`，9/9 PASS）**：真实派发 beforeprint、快照同步就位、
3 张位图且 ≥250 DPI、铺满 ≥80%、每页墨迹 > 0.002、**页数 ≤ 4**、
**非末页利用率 ≥ 80%**（p3 68.7% → 96.0% 就是这条抓出来的）、末页墨迹 > 0.005。

### 14.4 本轮环境坑（都在本机踩过，重跑前先看这段）

1. **`apply_patch` 工具在本会话不可用**（工具集里没有）：一律「PowerShell here-string 写片段
   → `node` 锚点脚本拼接」，锚点命中数 ≠ 1 直接抛错。
2. **vision skill 缺依赖**：`C:\...\codex-primary-runtime\dependencies\python` 里
   `openai/httpx` 缺 `idna / anyio / certifi / sniffio / distro / tqdm`，调用会直接 `ImportError`
   （不是 API Key 问题）。本轮已 `pip install idna anyio certifi sniffio distro tqdm` 修好；
   若换机器重装运行时需再补一次。
3. **PyMuPDF 不在该 python 里**（P4 轮的记忆说「可用」其实不准）：已 `pip install pymupdf`（1.28.2）。
   `render.py / ink.py / p3-pdf-report.py` 都依赖它。
4. **陈旧渲染 PNG 会伪造页数**：渲染目录必须先清空（见 14.2 开头）。
5. 探针端口：p6-word-charts=8801/9481（桩 LLM 8973）、p6-print-pages=8803/9483；
   老探针端口见第十二/十三节，别复用。
6. 变异脚本的锚点字符串里**不要用子串断言**验证 CSS：
   `page-break-inside: auto` 包含子串 `break-inside: auto`，曾让 M49 假通过；
   用例已改为按声明切分（`declarationsOf`）。

### 14.5 遗留与风险（诚实口径）

1. **Word / Excel 仍未在真机 Office / WPS 里打开过**（本机无 Office）：
   Word 侧证据是 python-docx（`inline_shapes` / 表格 / 样式）+ 直接读 `word/document.xml`
   与 `word/media/*` 字节 + vision 看内嵌图；Excel 侧同 P5。若用户在实际 Office 里看到异常，
   请回传现象截图。
2. **`PRINT_PREVIEW_LIMIT = 24` 是「约一页」的经验值**：不同数据集（图表数量、表行数）下
   不保证恰好填满；护栏是「非末页利用率 ≥ 80% + 页数 ≤ 4」这条真机断言，而不是「一定 4 页」。
3. **Word 图表尺寸上限 16.5cm × 20cm**：超宽/超长会被等比缩小（这是刻意的，防止溢出页边距），
   控制图这类竖长图在纸上会比屏幕矮一些。
4. **vision 对打印页的「留白」判断不可全信**：本轮 vision 说 p3 底部空 40~50%，
   而逐行墨迹剖面显示内容一直排到页高 91%（最后一行是表格第 6 行）。
   涉及「有没有内容 / 有没有留白」的量，以确定性剖面（bbox / ink）为准，vision 只作观感佐证。
5. 其余遗留同第十三节（DeepSeek 未实测、AI 结果不落盘、bundle ~2.2MB 等）。
